# LUNEX Website — Maintenance Guide

**Scope of this document**: everything about `lunex.cloud` — how it's built, why it's built that way, and how to change it safely. This is not about the specification or the repository; see `GITHUB-GUIDE.md` for that.

---

## 1. What the site is, in one paragraph

`lunex.cloud` is a single static HTML file — `index.html` — with all CSS and JavaScript inline in that same file. There is no build step, no framework, no package.json, no bundler. You edit `index.html` directly and upload it. This was a deliberate choice: the site is small enough (one page) that a build pipeline would add maintenance burden without adding value.

---

## 2. File structure

```
lunex-site/
├── index.html                    ← the entire site
├── LUNEX-Specification.pdf       ← linked from two places on the page (see below)
├── favicon.ico
└── assets/
    ├── favicon.svg
    ├── icon-180.png     (Apple touch icon)
    ├── icon-192.png     (Android)
    ├── icon-512.png     (Android / PWA)
    └── og-image.png     (1200×630 — LinkedIn/Slack/X link previews)
```

Upload this whole folder as the site root. Every path in `index.html` (`/favicon.ico`, `/assets/...`, `/LUNEX-Specification.pdf`) is root-relative, so the folder structure must be preserved exactly.

**`LUNEX-Specification.pdf` is not generated by anything in this site's own toolchain** — it's built from the repository (see `GITHUB-GUIDE.md` §5, `tools/pdf/build_pdf.py`) and then copied here as a plain static file. The site has no knowledge of its contents; it just links to it by a fixed filename from two places:

- The status card's "Read the spec (PDF)" button (`href="/LUNEX-Specification.pdf"`)
- The footer's "Specification" link (same href)

**Whenever the PDF is rebuilt in the repository, re-upload the new `LUNEX-Specification.pdf` to the site root, overwriting the old one.** The filename must stay exactly `LUNEX-Specification.pdf` — renaming it (even changing case) without updating both `href` attributes above will silently produce two broken download links on a live site, which is easy to miss since the rest of the page still works fine.

## 3. Design system

All colors and type choices live as CSS custom properties (`:root { --bg: ...; }`) near the top of `index.html`'s `<style>` block. Change a color there once and it propagates everywhere — never hunt for a hex code elsewhere in the file.

### Colors (exact values, same palette used in every diagram and the logo)

| Variable | Hex | Used for |
|---|---|---|
| `--bg` | `#FBFAF8` | Page background (paper) |
| `--ink` | `#16202B` | Primary text |
| `--muted` | `#5A6B7B` | Secondary text |
| `--navy` | `#1F3B57` | Primary brand color |
| `--navy-deep` | `#152A40` | Headlines, nav, footer background |
| `--green` | `#2E7D4F` | Accent — used sparingly, signals "this is the important bit" |
| `--blue` | `#2F6F9E` | Secondary accent |
| `--red` | `#B3402F` | Used only in the diagram illustrations, not site chrome |
| `--paper-line` | `#D6DEE7` | Borders, the grid background lines |

**If you ever need to reproduce or extend the palette**: pull the values from here, or from `brand/lunex-brand-concept.svg` in the repository — never eyeball a color from a screenshot. This project has a documented incident (see `docs/PROJECT-RECORD.md`, Phase 5) where a placeholder mark was hand-drawn instead of extracted from the source file, and it had to be found and corrected later.

### Typography

Three typefaces, loaded from Google Fonts (one `<link>` near the top of `<head>`):

- **Inter** — headings, navigation, buttons, UI chrome. Weights 400–800.
- **Source Serif 4** — body copy (paragraphs). Chosen deliberately over an all-sans-serif look to give the site a "specification document" gravitas rather than a generic SaaS-landing-page feel.
- **IBM Plex Mono** — anything representing a class name, file name, code snippet, or tag (`LunexObject`, `lunex-object-model.svg`, kicker labels like "01 — WHAT LUNEX IS"). Also used for the diagram node labels in the hero animation.

Never introduce a fourth typeface without a specific reason — the three-font system is intentional and covers every use case already.

### The grid-paper background

Applied via a `background` CSS property on `<body>`, using four stacked `linear-gradient()`s (fine grid every 22px, bold grid every 110px) plus the `--bg` color underneath. This is not a background-image file — it's pure CSS, which keeps the file self-contained with zero image dependencies for the background itself. It's also literally the same background pattern used in every one of the sixteen sub-model diagrams (`diagrams/*.svg` in the repository), which is why the site and the diagrams feel like one visual system rather than two separately designed things.

## 4. Page structure, top to bottom

```html
<nav class="top">          ← sticky nav bar: logo, section links, GitHub button
<header class="hero">      ← headline + the animated composite diagram
<section id="what">        ← "Five standards, one gap between them" — two-column
<section id="models">      ← all 16 sub-models, grouped into 4 colored bands
<section class="principle"> ← the naming-principle pull-quote
<section id="status">      ← "Early draft" status card with CTA buttons
<footer>                   ← links, license, mailto contacts
```

Each `<section>` has a numbered `.eyebrow` label ("01 — What LUNEX is", "02 — The specification") — if you add a new section, continue this numbering; don't skip or restart it.

### The four-band sub-model grouping

The `#models` section groups the sixteen sub-models into four colored bands, matching the layered structure used throughout the project (see `LUNEX-Specification.md` §3, "How to Read This Specification"):

| Band | Sub-models | Color |
|---|---|---|
| Foundation | 01–04 | `--navy` |
| Capability | 05–08 | `--blue` |
| Operator capability | 09–13 | `--green` |
| Autonomous layer | 14–16 | `--red` |

**When a sub-model's title changes** in the specification, it must be updated here too, in **three places on this one page**: the `.model-row` entry in this section, and — if it's referenced — the hero diagram's node count is unaffected (it shows numbers, not names) but the legend color-grouping would need to change if the four-band split itself ever changes. Two sub-model titles were found out of sync with the specification during this project (Sub-model 12 and Sub-model 15 were both missing their "& ..." suffix) — see `docs/PROJECT-RECORD.md` for that correction. **Always diff every mention of a sub-model's title against `LUNEX-Specification.md`'s actual section headings when either changes.**

## 5. The hero animation (the site's signature visual)

This is the most complex part of the page and the part most likely to need updating if the model itself changes (e.g., if a 17th sub-model is ever added).

### What it shows

A radial diagram: sixteen small numbered circles (01–16), arranged in a circle and grouped into the same four color-coded bands as the `#models` section, each connected by a thin line to one central circle labeled "LunexObject." On page load, the lines draw themselves outward from the center (a "pen plotting" effect), followed by the sixteen nodes fading in one by one, then the center hub, then a legend, then a caption. This is deliberately the *only* place on the page with this kind of animation — see `docs/PROJECT-RECORD.md`'s design reasoning: a page should spend its "animation budget" in one place, not scatter motion throughout.

### How it's built

The node positions are **not hand-placed** — they're computed with trigonometry (see the Python snippet pattern in `docs/PROJECT-RECORD.md`, the "radial layout" phase) so that:
- The 16 nodes are distributed proportionally by band size (4, 4, 5, 3 nodes get 4/16, 4/16, 5/16, 3/16 of the circle each).
- A fixed angular gap (20°, empirically the smallest gap that avoids node overlap at this radius and node size — a smaller gap was tried first and caused visible overlaps between adjacent bands) separates each band visually.

**If you ever need to regenerate this diagram** (e.g., sub-model count changes from 16), don't hand-edit the SVG coordinates — recompute them. The layout logic is:

```python
import math
layers = [("Foundation", "#1F3B57", [list of sub-model numbers]), ...]
total = sum(len(v) for _,_,v in layers)
cx, cy, R = 240, 210, 150   # center point and radius, in the 480×420 viewBox
gap_deg = 20
# for each layer, compute its angular span proportional to (count/total),
# minus gap_deg, then space its own nodes evenly within that span
```

Then verify programmatically (not just by eye) that every pair of nodes is farther apart than `2 × node_radius + margin` before rendering — this project caught a real overlap bug this way rather than by visual inspection alone.

### The animation mechanism (CSS)

Two CSS classes, applied as inline `style="animation-delay: Xs"` per element to stagger them:

```css
.draw{ stroke-dasharray:600; stroke-dashoffset:600; animation: draw 1.1s ease forwards; }
.fade{ opacity:0; animation: fadeIn .5s ease forwards; }
@media (prefers-reduced-motion: reduce){ .draw{stroke-dashoffset:0; animation:none;} .fade{opacity:1; animation:none;} }
```

`.draw` is applied to `<path>` elements (the connecting lines) — it works by animating `stroke-dashoffset` from the full dash length to zero, which visually "draws" the line. `.fade` is applied to `<g>` elements (nodes, labels, legend) for a simple fade-in. The `prefers-reduced-motion` media query disables both for users who've requested it at the OS level — never remove this; it's an accessibility requirement, not a nice-to-have.

**Verifying this after an edit**: don't just eyeball the finished state. This project's process was: render the page with a headless browser (Playwright) at multiple time offsets (e.g., 0.9s, 2.5s) to check the animation mid-flight and at completion, at both desktop and mobile (390×844) viewport widths, before shipping.

## 6. Assets: favicon and social preview image

These are not hand-drawn in an image editor — they're generated from code, for the same reason the hero diagram is: reproducibility. If the logo mark ever changes, regenerate these rather than patching pixels.

### The favicon set

Source: `assets/favicon.svg` — a small SVG containing **the real LUNEX logo mark** (the stacked, rotated squares with the green connector node), extracted directly from `brand/lunex-logo-light.svg` in the repository, at the correct proportions. From this one SVG, four PNGs are rendered at fixed sizes using a headless browser screenshot of the SVG at each target resolution:

| File | Size | Purpose |
|---|---|---|
| `favicon.ico` | 16×16, 32×32 (multi-res) | Browser tab icon, legacy support |
| `assets/icon-180.png` | 180×180 | Apple touch icon (iOS home screen) |
| `assets/icon-192.png` | 192×192 | Android |
| `assets/icon-512.png` | 512×512 | Android / PWA splash |

**The mistake to never repeat**: an early version of this favicon used a newly hand-drawn placeholder mark instead of the real logo, because it was faster to sketch something than to extract the real one. It looked plausible and shipped before anyone noticed it didn't match the actual brand mark used everywhere else (the website nav, the diagrams, LinkedIn assets). Always start from `brand/lunex-logo-light.svg` and crop/scale it — never redraw the mark from memory.

### The Open Graph (social share) image

`assets/og-image.png`, 1200×630px — this is what renders when the site's link is shared on LinkedIn, Slack, or X/Twitter. Built the same way: an HTML file with the exact brand colors/fonts, screenshotted by a headless browser, then downscaled from a 2× render for crisp text. Referenced in `index.html`'s `<head>` via:

```html
<meta property="og:image" content="https://lunex.cloud/assets/og-image.png">
```

If the tagline or headline text changes, this image should be regenerated to match — it currently duplicates the hero headline ("One object model for everything OT") and the sub-model/spec-page counts. A stale OG image (still saying "16 sub-models" after a change) is a small but real inconsistency risk if the model ever grows.

## 7. Contact addresses used on the site

- `info@lunex.cloud` — general contact (footer)
- `conduct@lunex.cloud` — Code of Conduct reports only (not linked from the site directly; lives in the repository's `CODE_OF_CONDUCT.md` and `SECURITY.md`)

Both are `mailto:` links, not a contact form — there is no backend, and none is planned. If a contact form is ever wanted, that's a bigger architectural change (needs a form-handling service like Formspree, or a serverless function) and should be treated as a deliberate decision, not a quick addition.

## 8. How to make common changes

**Add or edit body text (headline, section copy, etc.)**: edit the relevant text directly inside `index.html`. No rebuild needed — just re-upload the file.

**Add a 17th sub-model** (if that ever happens): update, in this order —
1. The `#models` section's band grouping and the new `.model-row`.
2. The hero diagram: recompute all 17 nodes' positions (see §5) and regenerate the `<path>`/`<g>` markup — don't just add one node to the existing 16-node layout, since the proportional band-angle math changes for every node once the total count changes.
3. The "sixteen sub-models" text mentions sprinkled through the page (search for "sixteen" and "16" case-insensitively).
4. The OG image (§6) if it mentions the count.

**Change a color**: edit the `:root` CSS variable once (§3) — do not search-and-replace hex codes, since a few colors (like the diagram illustration colors) are intentionally hardcoded to match the repository's diagrams exactly and shouldn't shift if the site's own accent color changes.

**Verify before shipping any change**: this project's standard practice, worth continuing —
1. Validate the HTML doesn't have unclosed tags (`python3 -c "from html.parser import HTMLParser; HTMLParser().feed(open('index.html').read())"` — it'll raise on malformed markup).
2. Screenshot at both a desktop width (~1400px) and a mobile width (390px) with a headless browser, and actually look at the render — don't assume responsive CSS "should" work.
3. If anything animates, check both an early and a fully-settled frame.

## 9. Deployment

Static file hosting — no server-side logic, no database, no environment variables. Any static host works (the site was designed assuming something like Netlify, Vercel, GitHub Pages, or a plain S3/CDN bucket). Deployment is: upload the `lunex-site/` folder contents to the host's root, done. There is no CI/CD pipeline for the website (unlike the PDF, which has a build script — see `GITHUB-GUIDE.md`).

**Don't forget `LUNEX-Specification.pdf` itself** (§2) — it's easy to redeploy `index.html` and the `assets/` folder after a content edit and forget that the PDF is a separate file that also needs to be present at the site root, since nothing in the deployment process enforces that the two stay together. If the PDF was rebuilt in the repository since the last deployment, upload the new copy at the same time as any other site update.
